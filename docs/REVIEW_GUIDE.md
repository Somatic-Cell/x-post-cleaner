# 共同レビューの進め方

目標は，ファイルを一つずつ読んで仕様と失敗時の挙動を確かめ，
最後に実アカウントへの接続を検証することです．
初版の段階で大規模な自動削除を実行する必要はありません．

## 第1回：仕様と純粋なロジック

対象は `rules.toml`，`domain.py`，`tests/test_domain.py` です．
まず，DELETE_CANDIDATE / KEEP / NEEDS_CONTEXT の境界を決めます．
「病んでいる人物」という属性を判定せず，どの種類の文面を整理したいかを定義します．
冗談・引用・単なる不満・技術的な否定的評価を，どう区別すべきかが主要なレビュー点です．

続いて `Period` の半開区間，IDの文字列表現，revision の意味，
モデル確率と confidence の区別，`auto_eligible` の条件を読みます．
ここで分類基準や自動削除条件に違和感があれば，API コードを読む前に修正します．

## 第2回：アーカイブと保存

対象は `archive.py`，`store.py` と対応テストです．
実アーカイブ全体を GitHub やチャットにアップロードする必要はありません．
まず `ingest` と `inspect` をローカルで実行し，ファイル構造・件数・対象期間を確認します．
対応外だった場合は，必要なフィールド名だけを保持した合成レコードで
失敗を再現し，パーサーと回帰テストを追加します．

レビュー点は，全件を読んだと言える対象範囲，文字化けや本文の省略，
同一IDの重複，本文の変更後に古い判定を使わないこと，一操作ずつのコミット，
同じDBの二重起動の禁止，DBに原文・訳文を複製する保存方針です．

## 第3回：削除の状態遷移

対象は `deletion.py` と `tests/test_deletion.py` です．
ネットワークの実コードより先に，本人照合，本文照合，承認，件数上限，
unknown からの回復を確認します．
「要求がサーバーへ届いた後に応答だけ失ったケース」を，
「要求そのものが失敗したケース」と混同しないことが中心です．

## 第4回：サービス接続

対象は `providers/` と `pipeline.py` です．
最初は実データを使わず，API契約・HTTP応答・秘密情報がログへ出ないことを確認します．
Jev は合成短文で応答形式を確認し，次に少数の本人投稿で性能を調べます．
原文 / 英訳 / 併記の3条件を同じ標本で比較し，翻訳の有無を決めます．
手動確認で候補に出た投稿だけを評価すると選択バイアスがあるため，
候補外の投稿も含む標本を用意する必要があります．

X は最初に読み取りだけで認証中のアカウントを照合します．
削除テストは利用者が意図して用意した不要な一投稿に限定し，件数上限を1にします．
CI は本物のアカウントに接続しません．

## 第5回：TUI と大量処理

対象は `tui.py` と `tests/test_tui.py` です．
この作成環境では Textual のインストールができなかったため，
最初に手元または CI で6件の headless UI テストを実行してください．
その後，Windows の実端末で日本語，折返し，長文スクロール，キー連打，
終了後の画面復帰，削除エラー時の表示を確認します．

## 今後追加する項目

別形式の長文投稿と編集履歴の扱い，アーカイブ取得後の差分同期，
ラベル付きの精度評価用データ形式，前の投稿へ戻る操作や選択の取消し，
分類の並列実行，課金予算ガード，推論エラーの一括再処理，
より強いデータ保護，OAuth 2.0 PKCE は未実装です．

まずは第1回をレビュー単位にすることを提案します．
変更ごとに関連テストを増やし，小さなコミットで追跡してください．

## GitHub に置く前の確認

`git status` / `git diff --cached` で秘密鍵，アーカイブ，SQLite，本文入りのログが
含まれていないことを確認します．最初の CI には API キーを設定しません．
リポジトリのライセンスと公開範囲は，所有者が決定します．
初回コミットには生成物ではなく，ソース，テスト，サンプルの設定，レビュー資料を含めます．
