# 設計

## 責務とデータの流れ

```text
archive.py ── ingest ──> SQLite posts
                          │
                          ├─ 期間抽出 ─> pipeline.py
                          │               ├─ Azure（選択式）→ translations cache
                          │               └─ Jev → assessments
                          │
                          └─ 確認対象の選択 → Textual の固定画面
                                                 │
                                                 └─ decisions を一操作ずつ保存
                                                        │
                      明示的に実削除を有効化した場合だけ ─┘
                                                        ↓
                                                deletion.py
                                       本人・版・承認・件数を検査
                                       現在の投稿者・本文を照合
                                       削除意図をDBへ先に保存
                                       X DELETE（一度だけ送信）
                                       成功 / 失敗 / 結果不明を保存
```

`domain.py` は値の検証と自動削除の適格条件，`store.py` は永続状態，
`providers/` はサービスごとの HTTP 形式，`pipeline.py` は翻訳/分類の順序，
`deletion.py` は削除の保護条件，`tui.py` は表示と操作，`cli.py` は構成・依存注入を担当します．
`demo.py` はテストとは別の，利用者が試せる合成データです．
本番の分類アダプターに，デモ用キーワード判定のフォールバックはありません．

## 同一性とキャッシュ

Post revision は ID・owner ID・日時・本文・注意フラグの SHA-256 です．
分類設定 profile も，送信形式の版・モデルの固定ID・ルール・入力方式・文字数ガード・
翻訳キャッシュ世代を含む SHA-256 です．DB は `post_id × revision × profile_id` に判定を保存します．
同じ本文でも判定条件が変われば新しい結果になります．

人間の選択は `post_id × revision` ごとです．「残す」を別の分類設定が上書きして自動削除する
経路はありません．ただし，本文/注意フラグ等が変わると確認対象の意味が変わるため，
以前の人間の選択は新しい revision に自動継承しません．
古い revision の本文の完全な履歴を残す履歴管理システムではありません．
再取込は現在の posts 行を更新し，元のアーカイブは別途保存する前提です．

翻訳のキャッシュはサービス・方式・原文・明示的なキャッシュ世代で識別します．
Azure 側のモデル版までは固定できないため，再現性は保存済みの訳文までです．

## DB と排他制御

SQLite の WAL と `synchronous=FULL` を使います．
同じ DB の二重起動を FileLock で拒否し，TUI の非同期 HTTP 処理中も DB を共有しません．
DB 操作自体はイベントループ上の同じスレッドで行います．
ネットワーク処理を待っている間の画面描画は可能ですが，大規模な同期 DB 操作には
専用のワーカースレッドを設けていません．現在の規模制限は ARCHIVE_FORMAT.md に記載しています．

保存表は posts，profiles，assessments，decisions，translations，deletion_state，events，meta です．
events は操作の追跡用であり，改ざん耐性のある監査ログではありません．
現在のスキーマ版は1で，自動マイグレーションは未実装です．

## 削除の状態

```text
未要求
  └─ DBへ削除意図をコミット → in_flight
                                ├─ data.deleted == true を確認 → deleted
                                ├─ 明確なHTTP拒否               → failed
                                └─ 通信切断/曖昧応答/中断       → unknown
```

起動時に残っている `in_flight` は `unknown` に移します．
成功応答を受け取った直後，結果のDB保存前に落ちた場合も unknown になります．
これは exactly-once を実現したという意味ではありません．
失敗した要求が実は成功していた可能性を安全側に扱う方式です．

`failed` / `unknown` は自動で再送しません．現在も同じ投稿が存在すると確認できた場合に限り，
明示的な reconcile によって手動再確認へ戻せます．404やアクセス拒否から削除成功を推定しません．

## 同時実行と性能の初期方針

分類は逐次処理で，1投稿ずつキャッシュを保存します．高速バッチ処理・並列分類は未実装です．
これは API 形式の簡略化ではなく，初版の実行スケジューリングの範囲です．
翻訳/推論の再試行は最大3回で，追加の利用料金が発生する可能性があります．
60秒を超えるサーバー指定待機は早すぎる再試行をせずに停止します．
削除は少なくとも18.1秒間隔とし，サーバーのレート制限情報がそれより厳しければ待機を延長します．
削除要求の自動再試行は一切行いません．
